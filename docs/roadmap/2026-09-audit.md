## 1. Executive summary

**OLOS is a substantial, working system with a thin planning layer.** Since April
2026 the team shipped a single Next.js 16 + Supabase application that runs the public
site, the onboarding funnel, a full Build Cycle formation pipeline, a weekly Learning
Log ritual with a hard gate, a Poderator dashboard, a Local Labs tenancy model, an
org-internal cycle track, a field-survey intake, a directory/feed social layer, and
an owner console. Verified size:

| Measure | Count |
|---|---|
| SQL migrations (`supabase/migrations/`) | 103 (`00001`–`00103`) |
| Tables documented in `SCHEMA.md` | 50 |
| API route handlers (`app/api/**/route.ts`) | 130 |
| Pages (`app/**/page.tsx`) | 82 |
| Cron routes / scheduled in `vercel.json` | 7 / 5 |
| Unit test files / passing tests | 67 / 627 |
| Markdown docs (`docs/**` + top-level) | 73 + 7 |
| Open issues / open PRs | 20 / 9 |
| Git history depth | 272 commits, 115 merges, **starting 2026-07-08** |

**Five headline findings**, in priority order:

1. **Three roadmap generations coexist and none is current.** `docs/OLOS-roadmap.md`
   (April; Waves 1–3) declares its own tracker stale. `docs/audit/IMPROVEMENT_ROADMAP.md`
   + `PROGRESS.md` (July 5; Phases 0–7) were last assessed at PR #161; the repo is at
   PR #389. `docs/requirements/implementation-plan.md` (July 12) sequenced the calendar
   overhaul into Cycle 3 and was partially executed. Nothing records what shipped
   between July 12 and today as a plan-vs-actual. See §2.
2. **Decisions are recorded in at least eleven places, none authoritative.** PRD
   decision logs, roadmap §5, the IMPROVEMENT_ROADMAP owner queue (14 items), the
   SOCIAL_LAYER queue (5), ORTELIUS §12 (8), SECTOR_MODEL §11, PRD-lab-lead §9,
   `scripts/ops/*.md`, migration header comments, PR bodies, and `feedback-running-list`
   🧭 rows. Open PRs #390/#391 propose the fix (an in-repo decision vault). See §3.
3. **The data layer is coherent in schema but ad hoc in operation.** The migration
   ledger has drifted from the files on both databases (issue #361: `00086`–`00100`
   applied out of band; `supabase db push` is unsafe). Eight hand-run prod SQL repairs
   live in `scripts/ops/`. Two crons that decide who gets emailed are dark. The cycle
   calendar exists in four representations. There is no metrics layer at all — the
   admin landing page shows "active / total enrolled" and nothing else. See §4.
4. **Issue and PR hygiene has lapsed.** 12 of 20 open issues carry no labels; the
   org's issue types (Task / Bug / Feature) are unused; there are no milestones; 6 of
   9 open PRs are documentation-only and have been open since July; #390 is a strict
   subset of #391. See §5.
5. **The persona layer stops at three roles.** `docs/personas.md` (May 20) defines
   Upskiller, Organizer, Moderator. The product now serves at least ten distinguishable
   roles, and the one the next sprint targets — the **pre-registrant** between cycles —
   is not described anywhere, though the code already has a `pre_registered` card
   state, a `getRecruitingCycle` resolver, and a `registered` enrollment status. See §6.

None of this is a crisis. It is the normal debt of a team that shipped ~390 PRs in
five months with Claude Code as a force multiplier and no documentation contract.
The fix is a contract plus enforcement ([`documentation-framework.md`](documentation-framework.md)),
not a rewrite.

### 2.2 What is missing entirely

- **A changelog.** Nothing records what shipped when, except merge commits. Git history
  itself only starts 2026-07-08 (the April–July history survives only in docs). This
  PR seeds `CHANGELOG.md` from the merge log and the docs' PR references.
- **A doc map.** Nothing tells a newcomer which of 80 files to trust. This PR adds
  `docs/README.md`.
- **Status headers.** Only the PRDs and requirements docs carry a status table. The
  others rely on prose ("Status: 2026-07, owner-ratified") or nothing.
- **A metrics dictionary.** No document defines "active", "engaged", "retained", or
  "at risk" in one place; five code paths define them independently (§4.5).
- **State-machine reference.** The enrollment vocabulary is spread across four
  migrations (`00037`, `00056`, `00099`, `00079`) and the reconciler header.

## 4. Data pipeline inventory

"Ad hoc" is precise here: each pipeline below is individually reasonable and was
built to solve a live problem, but nothing describes the set, and several write the
same state.

### 4.1 The enrollment state machine — one state, nine writers

`cycle_enrollments.status` is the load-bearing business state. Its CHECK constraint
admits **seven** values (`registered`, `active`, `inactive`, `revoked`, `stepped_back`,
`interested`, `completed` — `00037` + `00056` + `00099`). Verified writers of
`interested`/`completed`: **none** (dead vocabulary from the onboarding-redesign import).
`stepped_back` has no route (Phase 4, unbuilt). The live values are four.

| Writer | Transition | Path |
|---|---|---|
| Cycle interest / agreement | → `registered` | `app/api/cycles/[cycle_id]/interest`, `…/agreement` |
| Invitation fulfillment | → `active` then reconcile | `lib/auth/invitations.ts` |
| Reconciler | `registered` ⇄ `active` | `lib/enrollment/reconciler.ts` (called by pod register/withdraw, admin pod status, admin memberships, `ensureActivePodMembership`) |
| Revocation cron (dark) | `active` → warned → `inactive` + audit row | `app/api/cron/revocation-check` (unscheduled, #213) |
| Admin sweep | `active` → `inactive` + audit row | `app/api/revocations/check/[cycle_id]` |
| Admin reactivate | `inactive` → reconcile(recover) | `app/api/revocations/reactivate/[participant_id]` |
| Auto-recover on log | `inactive` → reconcile(recover) | `app/api/learning-logs` |
| Owner archive / reset / delete | → `revoked` / rows cleared | `lib/owner/*`, RPCs `00079`/`00080` |
| Cycle close-out | memberships stamped, pods `dissolved` | `lib/cycle/closeout.ts` |

The May 2026 incident (`architecture-review-onboarding-state-machine.md`) was exactly
this shape, and the reconciler fixed it well. What is missing is the **document**:
one state diagram, the writer table above, and a test that asserts the CHECK vocabulary
equals the code's vocabulary. See [`data-strategy.md`](data-strategy.md) §3.

### 4.3 Time — four models, one dual-write bridge

`docs/requirements/cycle-timeline.md` documents the four coexisting time models
(twelve naive `cycle_config` window columns, `phase_2/3_start` markers, the week grid,
and the hardcoded `anchor-events.ts`). Stage 1 (`00086`) made `cycle_phases`/`cycle_events`
the source of truth with a mirror back into the legacy columns. Verified today:
`_open`/`_close` still appears across ~22 UI files; `lib/cycles/anchor-events.ts` is
still the ceremony's data source; and the public `events` table drifted from both
until `00092` re-seeded dates by hand (`scripts/ops/anchor-date-drift-2026-07-29.md`).
The Stage 2 page sweep that retires the mirror is unrecorded.

### 4.4 Hand-run production SQL

`scripts/ops/` holds eight `.sql` files run by hand against prod, each with a
companion `.md` (a good pattern): dev/prod migration-ledger repairs (2026-07-06),
anchor-date drift and Luma merge (2026-07-29/30), the open-project-registration policy
change (2026-08-26), an energy-participants reset, and seeds. Issue #361 adds that the
CLI ledger itself is out of sync on both databases. **No table records that a given
ops script ran, when, by whom.** `owner_actions` (`00078`) is the right shape and
covers only console actions.

### 4.5 Five definitions of "engaged"

| Concept | Defined in | Reads |
|---|---|---|
| Weekly gate (locked/unlocked) | `lib/learning-logs/gate-logic.ts` | `learning_logs` since `log_due_at` |
| Compliance status (`on_track`/`due_now`/`behind`/`at_risk`) | `lib/learning-logs/compliance-logic.ts` | gate + at-risk run |
| At-risk run (consecutive missed weeks) | `lib/learning-logs/at-risk.ts` | week grid + logs |
| Pod health bands | `lib/moderator/log-health.ts`, `pulse-health.ts` | clarity/alignment averages, misses |
| Enrollment `active` | reconciler | pod membership reality |

These are internally consistent (the newest deliberately reuse the older), but no
document names them side by side, and the admin has **no aggregate view** of any of them.
The moderator Insights page (#381) is the only analytics surface in the product, and it
is pod-scoped by design.

### 4.6 Email — seven templates, one audit trail

Templates: invitation, registration confirmation, already-registered, learning-log
reminder, learning-log compliance nudge, leadership-log reminder, revocation warning.
`email_log` (`00057`) is written by **one** sender (the compliance nudge). Consequence:
no one can answer "what have we sent this member?", and idempotency is re-implemented
per cron (`invitations.email_sent_at`, "window younger than 24h", `email_log`).

### 4.7 Data collected but unsurfaced

From `SOCIAL_LAYER_ANALYSIS.md` §4, still true: `ai_experience_level`,
`availability_snippet`, `years_experience`, `slack_username`, `github_username`,
`drive_email`, `volunteer_interest`, `interest_areas`, `moderator_experience` are
collected and rendered nowhere member-facing. `role_intents` (mentor/volunteer) are
collected and drive no flow — the mentor pathway is Phase 5, unbuilt.

### 4.8 Exports

CSV contact exports exist at six scopes (cycle, pod, project, lab, all people,
authority) through one shared core (`lib/export/contacts.ts`) — well built, PII-heavy,
and the de facto "reporting layer". Every export is a full PII dump because there is
no aggregate alternative.

### 4.9 What is good and must be kept

- The reconciler pattern (one writer per lifecycle transition).
- Config-as-data (`cycle_config`), `cycle_id` on every domain table, stable identity.
- Idempotent, header-commented, `-- DOWN`-annotated migrations.
- The `DATA_ARCHITECTURE.md` §2 principles (provenance-first, longitudinal, versioned
  JSONB, governance columns).
- `scripts/ops` companion-note discipline, `is_test`/`is_staff` hiding, the testers
  pathway, member-view simulation with an audit table.
- 627 passing unit tests over the pure logic, plus `verify:cycle` end-to-end.
