## 0. How to use this brief

You are a fresh agent (or a lane in an Ultracode run) asked to build part of the onboarding experience before the next Build Cycle. Read in this order: §1 (where the code is and the branch rule), §3 (what is already decided — do not re-decide), §2 for the surfaces your lane touches, §4 and §5 for the rules that shape copy and mechanics, then your lane in §7 and the conventions in §8. §9 is a Workflow script for running the lanes in parallel. §10 lists the issues that own each piece; §11 lists the decisions the owner still has to make and what each blocks.

**The one-paragraph brief.** Between the Showcase (Oct 13) and the next kickoff, a person who signed up for The Labs sees a dead end: "No cycle running right now" or "We'll open your next steps here when it starts." The public pages still describe Summer 2026. The success team can write a weekly message only for weeks 0–12 and only to people who already logged. Poderators have a list of who needs a nudge but no goal, no record of reaching out, and a copy-prompt bundle that leaks the private tier. The program wants participants who seek information and act on their own, understands that not everyone wants the sensemaking half, and wants its own teams to practise the design method they teach. The lanes below make the public pages honest and cycle-aware, give the pre-cycle member two lists and a nine-step ladder, put the curriculum on the learning pages, give the success team a schedulable weekly-message table with its content already drafted, give Poderators a self-set weekly outreach goal and a safe logs query, and set the decisions for three honest ways into the cycle.

## 4. The behavioral evidence base, and the rules it gives every lane

The organisation's goal for participants is **proactive, information-seeking, high-agency behaviour**: scope a problem, seek out and talk to stakeholders, interview to build personas, iterate. The framing that makes this coherent with the constitution is Hertwig & Grüne-Yanoff's distinction between **nudges** (change the choice environment; effects small and gone when the environment changes — real-world nudge effects are roughly a sixth of published academic ones) and **boosts** (build a competence that persists after the platform is gone). OLOS builds boosts and uses only transparent, cheap, consented nudges (a dated reminder, a default). Classify every feature as one or the other before building it.

### 4.1 Interventions, honestly rated, and where they land

|---|---|---|
| **Implementation intentions** (Gollwitzer 1999; Gollwitzer & Sheeran 2006 meta-analysis) and **plan-making prompts** | Strong in lab and field for people who already hold the goal; digital low-touch effects are single-digit points and heterogeneous (Kizilcec et al. 2020) | Pair every ladder step and weekly task with a named day and place; the `.ics` is the first ask after pre-registration; weekly messages end with a two-blank plan line; the Poderator names the day and channel for outreach. | **Mental contrasting / WOOP** (Oettingen et al. 2001; Oettingen 2014) | Moderate (g ≈ 0.34, publication bias flagged; halves when delivered by document) | Optional four-box close to M0, stored privately, shown back to the member at week 6 and Showcase; a Poderator script to run it aloud in the first pod call |
| **Self-determination theory** (Deci & Ryan 1985; Ryan & Deci 2000, 2017; Reeve 2009 on autonomy support) | Strong theory; moderate intervention effects; controlling language reliably undermines | The ladder is a menu with a rationale per step and "not for me"; every ask carries a why; a real alternative in every drip; three honest ways in on the cohort page; informational, never controlling, feedback |
| **Self-efficacy from mastery** (Bandura 1977, 1997; Bandura & Schunk 1981). Growth-mindset copy: near-zero meta-analytic effects (Sisk et al. 2018; Macnamara & Burgoyne 2023) — do not build on it | Strong for mastery > vicarious > persuasion | Each pre-cycle item ends with a ten-minute task that yields a kept artefact (intro posted, GitHub profile, a readable extraction); the first three ladder steps are certain wins; spotlights chosen for similarity, not stardom |
| **Goal-setting theory** (Locke & Latham 1990, 2002; Seijts & Latham 2005 on learning goals; Ordóñez et al. 2009 "goals gone wild") | Strong; learning goals beat performance goals for novices; numeric quotas corrupt | Weekly tasks are discovery goals ("find out who has already tried"); the Poderator's weekly goal is self-set from a default, private, with the loop as feedback — never a quota shown to admins per person |
| **Information-gap curiosity** (Loewenstein 1994; Kang et al. 2009; Gruber et al. 2014) | Moderate; trivia paradigms replicate, extrapolation to inquiry is design rationale | Open each module and each sensemaking week with a concrete, locally specific, unanswered question the member can only close by leaving the platform; the following week reports what the cohort found. Manufactured cliffhangers are banned |
| **Commitment devices / foot-in-the-door** (Bryan, Karlan & Nelson 2010; Freedman & Fraser 1966; Gollwitzer et al. 2009 caution on public identity goals) | Moderate–strong for self-selected devices; public identity goals can backfire | The Open Cycle Agreement stays a plain, dated, voluntary promise to concrete actions; the "Joining {cycle}" directory chip is a public commitment to a dated event, never to an aspiration; "step back" is always available without penalty |
| **Fresh-start effect** (Dai, Milkman & Riis 2014, 2015; Beshears et al. 2021) | Moderate; effects on starting, single-digit points | Anchor the big asks to real landmarks: Showcase day, the first working week of January, T-1w, week 0; Monday sends named by week and date; week 7 and any post-miss week framed as a clean start. No manufactured anniversaries |
| **Endowed progress** (Nunes & Drèze 2006; Kivetz, Urminsky & Zheng 2006) | Moderate; credible head starts only | The ladder renders at 2/9 or 3/9 from real facts (lab, photo, pre-registration); never inflated; capped at nine |
| **Social proof, focus theory of norms, dynamic norms** (Cialdini, Reno & Kallgren 1990; Schultz et al. 2007 boomerang; Sparkman & Walton 2017) | Strong at 1–5 points at scale; boomerang replicated | Local descriptive norms above the floor, phrased dynamically with an injunctive cue ("19 neighbours in DC are pre-registered, six this week, and they'd like you there"); never rank; never show who has not logged to peers |
| **Habit formation and cues** (Lally et al. 2010; Wood & Neal; 2024 reviews) | Moderate–strong; weekly habits form slowly; a single miss does not derail | Fix the Friday cue (same day, hour, entry point); introduce it at T-2w and T-1w with a practice log; Tuesday is the Poderator's cue. No streaks, no "don't break the chain" |
| **Open loops (Zeigarnik / Ovsiankina)** | Weak and contested | Use only negatively: show the single next step, offer a plan to finish a started step once, then silence; never persistent red dots |
| **Peer accountability, cohort and belonging** (Tinto 1993; Walton & Cohen 2011; Walton et al. 2023; Carrell, Sacerdote & West 2013 as the caution) | Moderate; engineered peer groups backfire | The pod is the accountability unit, not the platform; a first-person belonging story in M0 and T-2w from a similar prior member; pods form on member choice within a lab |
| **Psychological ownership and the IKEA effect** (Pierce, Kostova & Dirks 2001; Norton, Mochon & Ariely 2012; Marsh et al. 2018) | Moderate; conditional on completion | The write-up fills from the member's own logs and is exportable; stakeholder maps and personas are member-authored, versioned artefacts; the directory card is theirs |
| **Spacing and retrieval practice** (Cepeda et al. 2006, 2008; Roediger & Karpicke 2006; Rowland 2014; Adesope et al. 2017) | Strong | One module per drip week, spaced T-6w…T-1w, never a bundle at sign-up; one private, ungraded recall question two weeks later; weekly messages open with a one-line recall of last week's step |
| **Worked examples, cognitive load, productive failure** (Sweller 1988; Kirschner, Sweller & Clark 2006; Kapur 2008; Sinha & Kapur 2021) | Strong for novices; productive failure moderate | Skill modules run: bounded attempt on the member's own problem → annotated example from a prior pod (with consent) → faded template; the first Learning Log shows one worked example beside the blank |
| **Tutoring and mentoring** (Bloom 1984 corrected by VanLehn 2011; Nickow et al. 2020) | Strong that structured, frequent human contact works at 0.3–0.8 SD, not 2 SD | The Poderator's weekly contact as a structured ritual (one question per quiet member); the mentor briefing page; "who to ask" on every module |
| **Underestimating others' willingness to help** (Flynn & Lake 2008; Bohns 2016; Roghanizad & Bohns 2017; Liu et al. 2023 on appreciation) | Moderate–strong; the largest single barrier to information-seeking | State the finding plainly as a boost, give a two-sentence ask script and the honest base rate, and make "find one person who…" the atomic task of weeks 2–5; tell Poderators quiet members appreciate a check-in more than they think |
| **"First-week activation"** (practitioner accounts; MOOC literature) | Practitioner, correlational | Treat "ladder ≥ 6 by kickoff" and "first log within 7 days" as hypotheses to test from tables, never as targets to game |
| **Gamification** (Hamari et al. 2014; Sailer & Homner 2020) | Weak and unstable; leaderboards harm non-top performers | Do not build. Cite in review when rejecting streaks, badges, leaderboards |

### 4.2 Ten design rules for high-agency behaviour (apply to every screen and message)

1. **Ask first, then tell.** A two-to-five-minute attempt on the member's own problem, then a worked example from a prior pod, then the template. Never open with the template.
2. **Questions are the tasks; answers live off-platform.** Weekly tasks are questions that require leaving OLOS ("who signs off on this?"); the log asks for the answer and how it was obtained.
3. **"Find one person who…" is the atomic unit of work**, with a two-sentence ask script and the honest base rate.
4. **Visible, real choice at every stage**: three honest ways in; "not for me" on every self-attested step; a default and one alternative in every weekly task.
5. **Stakeholder-map and persona tasks require leaving the platform and coming back with evidence**; the map is the pod's own, versioned, with named contributors.
6. **Reflection prompts ask for evidence, not sentiment** ("what did you learn, from whom, with one example"). No mood sliders as the primary prompt.
7. **Rationale before every ask**; a one-line "why" on every step, message, task, and goal.
8. **Close the loop with what happened, never with how much was done**: "you reached 3, 2 logged"; "the cohort found 31 decision-makers". Counts are consequences, never comparisons.
9. **Hand over portable tools, then step back**: each module ends with an artefact the member keeps (interview card, safety rules, extraction prompt, outreach template). Test: could they use it after the Labs without OLOS?
10. **Normalise being behind; make the next step the only step.** Neutral, forward copy once; one finishable step; a plan prompt; no red counts, no "overdue", no streak language.

### 4.3 Anti-patterns (review checklist; reject on sight)

Leaderboards or any per-person comparison · streaks and loss-framed reminders · badges as public clout · countdowns, "3 spots left", manufactured deadlines · curiosity clickbait · counts below the floor or peer-visible absence lists · reminder cadences that vary by engagement (needs telemetry) · auto-scheduled follow-ups keyed to private plans or WOOP answers · numeric Poderator quotas surfaced to admins per person · growth-mindset exhortation as the lever · front-loading all modules at sign-up · unguided "go figure it out" for first-timers · algorithmic pod composition · time-on-page, scroll, open-rate metrics · "TUL", "user", "lead", "registrant", or the manager voice.

### 4.4 Curriculum principles (for lane L and the success team)

One module per drip week, each under 20 minutes; every module ends with a mastery task that produces a kept artefact in under ten minutes; attempt → worked example → faded template; one private recall question two weeks later; teach the ask before the method (the interview module states the compliance base rate); design thinking taught as a sequence of questions answered with evidence (a name, a quote, a document, a count), not as a diagram; tool onboarding framed by what it makes possible, with the three AI-safety rules as the non-negotiable core; a human endpoint ("who to ask") on every page; three entry points described honestly, each with its own pre-cycle path; a belonging story in M0 from a similar prior member, with consent.

### 4.5 What to measure (from tables, never telemetry)

Drip sends by kind/cycle/audience with consent and unsubscribe rates (`email_log`); ladder steps completed by kickoff (distribution; share ≥ 6 of 9; verified vs self-attested; by sub-persona); pre-registered → active within 14 days of kickoff; first Learning Log within 7 days of kickoff (and of pod formation for late joiners); weekly log compliance trend by cohort and lab (aggregate only); Poderator outreach → response (entries per week; share who logged within 7 days; median days) — the Poderator sees their own, admins see per-pod aggregates; stakeholder conversations logged per pod and cohort; share of pods naming a decision-maker by week 3; field-survey observations and shares by pre-registrants (above floor); share-line reach and write-up completion, private to the member; recall-question answered (presence, ungraded) and "not for me" reasons; alumni pathway take-up within 3 weeks of Showcase; the one lapsed nudge's return rate; per-role journey-review findings per cycle. **Explicitly not measured**: time on page, scroll depth, email opens, click heatmaps, per-member activity streams, read receipts, per-Poderator quota attainment.

## 5. Frame innovation, the cycle, and the three ways in

The Labs thinks about its method through Kees Dorst's **frame innovation** (Dorst, *Frame Innovation: Create New Thinking by Design*, MIT Press 2015; "The core of design thinking and its application", *Design Studies* 2011). The nine frame-creation steps, in one line each: **Archaeology** (how the problem was framed and what was tried), **Paradox** (the two true things that cannot both be satisfied: "because A, B; but because C, not B"), **Context** (the inner circle of stakeholders and their practices), **Field** (the wider circle of players who could be part of a solution, and what moves them), **Themes** (the deeper needs and values running through the field), **Frames** ("IF we see the situation as X and adopt its working principle, THEN…"), **Futures** (design forward from the frame and test whether it leads somewhere valuable), **Transformation** (what must change in the organisation and among stakeholders for it to hold), **Integration** (fold the frame into lasting practice). The nine names are Dorst's; the one-line glosses here are paraphrases.

### 5.3 The narrative for participants (public copy, plain words)

> You came to The Labs to build something. Here is why we ask you to look before you build.
>
> Most problems worth your time have been worked on, by people who cared, and they are still stuck. It is because the problem was framed in a way that could not be solved. Two things are true at once and pull against each other. The office fridge is disgusting because everyone is saving lunch they mean to eat, and everyone is furious when it gets purged for the same reason. Clean it harder and you will be cleaning it forever.
>
> So the first weeks of a Build Cycle are for finding that knot. You will share a short survey with people who live near the problem and read what comes back. On a Saturday in week two you will sit with strangers and write, in one paragraph, what stays stuck no matter what people try. Then you will go and ask the people nobody asked, two conversations, thirty minutes each, and write down what surprised you. Somewhere in there the problem turns, and a new way of seeing it appears. That is your frame, and it is what you build against.
>
> What you leave with: a prototype you tested with a real person, a written record of every decision your pod made and why, a public Showcase, and a habit: knowing where to start when something is stuck. You also leave with a pod, five to fifteen people who watched you think and will vouch for you.
>
> If you would rather build than research, the Hackathon opens the door. You will inherit a frame someone else found. Read their notes first. Then make something bad, quickly, and find out what is true.

## 8. Lane conventions — parameters and submission criteria every lane inherits

**Branching.** `git fetch origin dev && git checkout -b <lane-branch> origin/dev`. One
lane, one branch, one PR into `dev`. Conventional-Commit PR title (`feat(dashboard): …`,
`content(weekly-messages): …`, `docs(…)`). Never push to `dev` or `main`.

**Definition of done (the PR is not ready until all of these are true).**

| Check | How it is enforced |
|---|---|
| `npm run lint && npm run test && npm run build` green | `ci.yml` on the PR |
| `npm run check:docs` green — relative links resolve, vault frontmatter valid, migration numbers unique | `docs-check.yml` |
| A `CHANGELOG.md` line under **Unreleased** ending in `(#PR)` for any change under `app/`, `lib/`, `supabase/`, `proxy.ts`, `vercel.json` | `docs-check.yml` (opt-out label `skip-changelog` + a reason) |
| A migration ⇒ `SCHEMA.md` updated in the same PR, number claimed on the issue first | `docs-check.yml`, `npm run check:migrations` |
| A choice was made or the build moved off a spec ⇒ a note in `docs/vault/` (MADR shape; status `proposed` until the owner accepts) | PR template "Docs & decisions"; reviewer |
| A new page or dashboard mode ⇒ a wireframe linked from the issue **before** sizing, filed in the knowledge repo `program/design/wireframes/` | issue [#446](https://github.com/TheUpskillingLabs/OLOS/issues/446); reviewer |
| Copy follows `DESIGN_SYSTEM.md`: "The Labs" (never "TUL"), "Poderator" (never "moderator" in UI), "Upskiller"; warm, concrete, dated, one next step | reviewer |
| Design tokens only (`--ink`, `--teal`, `--paper`, …); phone width first; the shared `app/components/ui/form.tsx` has one owner at a time | reviewer; `docs/agent-teams.md` ownership map |
| Constitution: no in-app LLM; the platform is a shepherd, not a manager; no activity telemetry or read-tracking; nothing shames a person who is behind; consent-gated messaging; Poderator-only signals never render for members; `is_test`/`is_staff` excluded from every count | reviewer with the "constitution" lens (§9) |
| No names of real participants in any committed prose (OLOS is public); roles and ids only | reviewer |
| The PR body names the issue it closes (`Closes #NNN`) and links the wireframe, the vault note, and the screenshots (phone + desktop) | PR template |
| A session report in `docs/sessions/YYYY-MM-DD-<slug>.md` for the session that did the work (template in `docs/sessions/README.md`) | `CLAUDE.md` rule; reviewer |

```js
const ground = (lane) => agent(`Read ${BRIEF} §2–§6 and the lane ${lane.key} row in §7, then the issues ${lane.issues.join(', ')} (use the GitHub MCP tools via ToolSearch), then the files under ${lane.owns.join(', ')}. Write the implementation plan: files to change, the copy deck (every user-facing string, in the brief's voice), the states, the tests, and the risks. Do not edit files.`, { label: `ground:${lane.key}`, phase: 'Ground', schema: PLAN })
const build = (plan, lane) => agent(`Implement lane ${lane.key} on a new branch ${lane.branch} from origin/dev (git fetch origin dev first). Plan: ${JSON.stringify(plan)}. Own only ${lane.owns.join(', ')}; never edit ${lane.avoid.join(', ')} — file an issue instead. Follow ${BRIEF} §8 (definition of done) exactly: changelog line, SCHEMA.md if a migration, vault note if a choice, tests for lib/ helpers, phone-width check. Commit in small Conventional Commits. Do not push and do not open a PR. Return the branch, the commit list, and what is still open.`, { label: `build:${lane.key}`, phase: 'Build', isolation: 'worktree', agentType: lane.zone, schema: RESULT })
const review = (result, lane) => parallel(LENSES.map((l) => () => agent(`On branch ${result.branch} (git diff origin/dev...${result.branch}), review lane ${lane.key} through the ${l.key} lens. ${l.prompt} Report only findings you can point to by file and line; default to "no finding" when unsure. Do not edit.`, { label: `review:${lane.key}:${l.key}`, phase: 'Review', schema: FINDINGS }))).then((rs) => ({ result, findings: rs.filter(Boolean).flatMap((r) => r.findings) }))
const fixAndVerify = ({ result, findings }, lane) => agent(`On branch ${result.branch}, fix these findings (skip any you can refute, and say why): ${JSON.stringify(findings)}. Then run npm run lint && npm run test && npm run build && npm run check:docs and fix until green. Write the session report docs/sessions/<date>-lane-${lane.key}.md. Commit. Do not push. Return the final state.`, { label: `verify:${lane.key}`, phase: 'Verify', isolation: 'worktree', agentType: lane.zone, schema: RESULT })

const parallelLanes = LANES.filter((l) => !l.singleOwner)
const serialLanes = LANES.filter((l) => l.singleOwner)  // P, then C (C waits for U's branch to exist)
const done = await pipeline(parallelLanes, ground, build, review, fixAndVerify)
for (const lane of serialLanes) {                     // single-owner zone: one at a time
  const plan = await ground(lane)
  const built = await build(plan, lane)
  const reviewed = await review(built, lane)
  done.push(await fixAndVerify(reviewed, lane))
}
return done.filter(Boolean)
```

**What the lead (you) does between phases.** Read each lane's plan and copy deck before
`Build` runs at scale (edit the `LANES` array and resume the run if a plan is wrong);
push each verified branch yourself with `git push -u origin <branch>` and open the PR
into `dev` only when the human asks for one; paste the workflow's final report into the
session report.
